# Undara — Agent, Design System & Engineering Rules

These rules apply to the entire repository unless a more specific implementation requirement says otherwise.

## 1. Required Workflow Before Coding

Before any material change, inspect in this order:

1. `AGENTS.md`
2. `prd.md`
3. `README.md`
4. Relevant implementation files, routes, components, schema, and APIs

`prd.md` is the single source of truth for active product requirements **and** the consolidated implementation history in Appendix A.

Every AI-made material change MUST update Appendix A in `prd.md` with rationale, affected files/area, commit(s), and validation status. If a change alters product requirements, update the canonical body section first and then append its implementation/history entry in the same `prd.md`.

Do not create or revive split PRD files (`prd1.md`, `prdnew.md`, `PRD2.md`, etc.). Legacy `prd-tambahan.md`, `prd-landing.md`, `prdpaging.md`, and `pintu3d.md` were retired from the active branch after owner-directed cross-check; historical content is available via permalink Git in `prd.md` Appendix A. Never recreate them as parallel rulebooks. Update the relevant canonical product section in `prd.md` and (for material changes) Appendix A. Follow the status/authority map in `prd.md` §21.

Do not add generic project-wide prompt/skill documents that duplicate or conflict with `AGENTS.md` and `prd.md`. If specialized instructions are genuinely needed, keep them narrowly scoped and explicitly referenced.

Validation must distinguish source inspection, actual build/CI results, database migration, and browser/E2E verification. Never describe build/CI/migration/E2E as PASS without direct observed evidence for the relevant commit and environment.

**Owner implementation workflow (28 September 2026):** For Undara repository tasks, when the owner asks to change/fix/continue coding, the default is to **inspect the current repo, implement the change directly in GitHub, run/observe the relevant regression/build checks, and report the resulting commit/status**. Do not hand the owner code snippets to copy-paste as a substitute for repository work unless the owner explicitly asks for code only, asks not to modify the repo, or the required repository/tool access is unavailable. Keep edits narrowly scoped to the requested change and preserve unrelated approved behavior.

**Design skill + Library workflow (30 September 2026):** For any material frontend design, redesign, visual polish, invitation art direction, motion, or UI-quality task, agents MUST read `.agents/skills/undara-design/SKILL.md` in addition to the normal repository workflow. Project truth always wins in this order: **explicit owner request → `prd.md` → `AGENTS.md` → scoped docs such as `template.md` / `studio.md` → current source/tokens/components/assets → external design skills**.

Design work must not rely only on model memory. Before implementation:
- discover the runtime's installed/global design skills and use the relevant one when available;
- inspect project/shared Library resources and reusable components/assets before inventing a new primitive;
- if an expected globally installed skill is not exposed in the current runtime, read the pinned upstream `SKILL.md` listed in `.agents/skills/undara-design/SKILL.md` and apply its method honestly;
- never claim a global skill was invoked when the runtime did not expose it;
- do not silently skip Taste/Emil/Impeccable merely because their package is absent from this repository.

The default Undara design stack is:
- **GPT Taste / `gpt-taste`** for art direction, composition, hierarchy, whitespace, layout variance and anti-generic output;
- **Emil Kowalski `emil-design-eng` + `animate` / `review-animations`** when interaction or motion materially matters;
- **Impeccable** for bounded critique, polish, audit, harden/adapt and final quality review.

Use the stack deliberately, not mechanically. Do not run every skill for every tiny edit. For invitation themes, always read `template.md` first. For Studio editing behavior, read `studio.md`. The shorthand **`to design`** means apply this design workflow to the requested scope; it does not expand the requested scope by itself.

**Web-invitation-first Studio rule (27 September 2026):** Canva/Figma-like behavior applies to the **authoring interaction only**. Undara output remains a responsive web invitation with section ownership, normal document/scroll flow, mobile/desktop behavior, semantic interactive DOM, and the shared RSVP/Maps/Countdown/Music/Wishes/Gift/data engines. Never turn invitation rendering into one global fixed-size poster/artboard or blanket absolute-position all content. Free transforms must remain section/component-scoped, editor zoom/pan/handles must not leak into public layout, and Designer/Owner freedom must preserve responsive usability and protected web functionality.

**Designer/Customer Studio scoped rule (24 September 2026):** Before modifying designer template authoring, the invitation canvas, visual properties of shared components, or custom-made workflows, read `studio.md` as the scoped design and authorization rule alongside canonical `prd.md` §7.2.0c and `template.md`. Designer may modify whitelisted visual presentation across sections, including reversible removal of any registered visual target, but must never rewrite or bypass protected component behavior, event data, business APIs, or customer permissions. Delete hides presentation without deleting source records/files; sections may be emptied and Restore Defaults must bring built-in visuals back. `studio.md` describes future requirements and must not be mistaken for already implemented functionality.
